--------------------------------------------------------------------------------
A1. Abstention confound: "ClosedBook beats NaiveRAG on 2Wiki" is an artefact
    of answer length, not of the model's knowledge.
--------------------------------------------------------------------------------
WHERE
  pkg/rag/naive.go (buildPrompt), pkg/rag/closedbook.go (buildClosedBookPrompt),
  cmd/bench/main.go (result, dumpRecord, evaluate, aggregation and .tex output)

WHAT IS WRONG
  When retrieval fails, the reader that HAS context refuses to answer
  ("The provided documents do not contain information about ..."), which scores
  Exact Match 0. The closed-book reader has no documents to refuse over, so it
  guesses, and a guess is sometimes right. The reported closed-book advantage
  on 2WikiMultihopQA therefore measures willingness to abstain, not knowledge.

EVIDENCE (measured from runs/)
  mean words per answer / share of answers > 20 words / EM of those long answers
      closedbook-2wiki      3.44 /  2.3% / 0.000
      naive-2wiki           9.20 / 16.8% / 0.000
      naive10-2wiki         7.78 / 13.1% / 0.000
      ircot-2wiki           8.41 / 14.5% / 0.000
      closedbook-hotpotqa   3.05 /  2.0% / 0.000
      naive-hotpotqa        6.72 / 11.4% / 0.000
      closedbook-musique    7.56 / 13.2% / 0.000
      naive-musique        13.22 / 26.5% / 0.000
  On 2Wiki, restricted to the 10,464 questions where naive answered in <= 20
  words:  naive EM 0.2625  vs  closedbook EM 0.2555  (naive wins).
  On the 2,112 questions where naive produced a long refusal (EM 0 by
  construction), closedbook scores EM 0.1889.
  Example (2Wiki):
    Q    "Where was the place of death of the director of film Beat Girl?"
    GOLD ["Nice", "Nizza", "Nice, France"]
    RAG  "The provided documents do not contain information about a director
          named for a film titled 'Beat Girl'. There are mentions of films
          called 'Beat' but in different contexts ..."         -> EM 0
    CB   "Los Angeles, California, USA"                        -> EM 0

WHAT TO DO
  1. Add an abstention metric to pkg/metrics (new file abstention.go):
       func IsAbstention(answer string) bool
     Detect both signals, because either alone is leaky:
       - length: more than 20 whitespace-separated tokens, AND
       - refusal phrasing: normalised answer contains any of
         "do not contain", "does not contain", "no information",
         "not mentioned", "cannot answer", "can not answer",
         "not provided", "no mention", "unable to answer",
         "not enough information", "insufficient information".
     Return true if the refusal phrasing matches, or if the answer is longer
     than the length threshold. Make the threshold a named constant and a
     cmd/bench flag (-abstention-max-words, default 20) so it can be ablated.
  2. In cmd/bench: score it per question, add `abstained` to `result` and
     `"abstained"` to dumpRecord, print "Abstention rate: X" in the summary,
     and emit \<Name>AbstentionRate in the .tex.
  3. In cmd/bench: additionally report EM and F1 over the non-abstained subset
     ("EM (answered only)"), with its own question count, and emit
     \<Name>EMAnswered / \<Name>FOneAnswered / \<Name>AnsweredQuestions.
  4. In cmd/compare: add "Abstention" as a reported metric (mcnemar), and add
     a paired EM comparison restricted to questions where NEITHER system
     abstained. Emit both into the .tex.
  5. In cmd/diagnose: the closed-book comparison block must report abstention
     rate alongside EM in the retrieval-succeeded / retrieval-failed split.

WHY IT MATTERS FOR THE PAPER
  This is simultaneously (a) a correction that reverses a headline claim and
  (b) the strongest motivation for the new retrieve-or-abstain architecture:
  the current metrics punish an honest refusal exactly as hard as a wrong
  answer, while the oracle over {closed-book, RAG} is worth +0.1026 EM on
  2Wiki (see paper/diagnosis-2wiki.gen.tex, \DiagTwoWikiOracleGain).

HOW TO VERIFY
  Re-score existing dumps offline: runs/*.jsonl already contain "answer" and
  "gold", so a small script can compute abstention rate and answered-only EM
  WITHOUT re-running any model. Expected: 2Wiki naive abstention ~16-17%,
  closedbook ~2%, answered-only EM naive 0.2625 vs closedbook 0.2555.

A2. AnswerInContext is broken: raw substring match with no word boundaries.
--------------------------------------------------------------------------------
WHERE
  pkg/metrics/answercontext.go:29  ->  strings.Contains(p, ng)

WHAT IS WRONG
  Both sides are normalised and then compared as raw substrings, so a gold
  answer "no" matches inside "not", "now", "north", "known", "nobody".
  Any short gold answer is affected.

EVIDENCE (measured on runs/naive-2wiki.jsonl)
  gold == "no"    n=346   answer_in_context = 0.9740   (spurious)
  gold == "yes"   n=949   answer_in_context = 0.0369
  gold <= 3 chars, non-yes/no   n=415   answer_in_context = 0.7759
  all other questions           n=11281 answer_in_context = 0.3490
  On runs/naive-hotpotqa.jsonl: short (<=3 chars) 0.6541 vs other 0.5435.

WHAT TO DO
  1. Rewrite AnswerInContext to match on TOKEN boundaries, not characters:
     normalise both sides, split into tokens with strings.Fields, and search
     for the gold token sequence as a contiguous sub-slice of the passage
     token sequence.
  2. Add a bool return or a separate helper reporting whether the metric is
     APPLICABLE, and make it not applicable when the gold answer set is
     exactly {"yes"} or {"no"} (case-insensitive after Normalize): a boolean
     question has no answer span in the text, so scoring one is meaningless.
  3. In cmd/bench: aggregate answer-in-context only over applicable questions,
     the same way Recall@K is already gated on hasGold. Report the applicable
     question count and emit it into the .tex
     (\<Name>AnswerInContextQuestions).
  4. In cmd/compare: gate the "Answer in context" row the same way.

KNOCK-ON EFFECT (important)
  cmd/diagnose selects the questions to diagnose with `r.InCtx == 0`
  (cmd/diagnose/main.go, the `failed` loop). With the current metric, almost
  no question whose gold answer is "no" is ever diagnosed, and many questions
  with short answers are wrongly treated as retrieval successes. All
  paper/diagnosis-*.gen.tex numbers must be regenerated after this fix.

HOW TO VERIFY
  Unit-check by hand (no tests are to be committed - see CLAUDE.md, just check
  locally and delete): passage "he was not born in Paris", gold "no" -> 0.
  Then confirm 2Wiki gold=="no" answer-in-context drops from 0.974 to
  something close to the gold=="yes" figure, or that those questions are
  excluded entirely.
  NOTE: this cannot be recomputed from runs/*.jsonl today, because the dumps
  do not store the retrieved passages. Do B1 FIRST, then this becomes an
  offline recomputation instead of a full GPU re-run.

A3. The Recall ceiling is far below 1.0 and is not reported anywhere.
--------------------------------------------------------------------------------
WHERE
  new: cmd/coverage (small standalone command), plus a row in every results
  table in the paper.

WHAT IS WRONG
  A large share of the gold articles annotated by the question sets simply do
  not exist in wiki18_100w. A perfect retriever cannot exceed that share, so
  the reported Recall@K is unreadable without it, and looks inexplicably low
  next to published numbers.

EVIDENCE (measured: all 3,232,908 corpus titles extracted and intersected with
the gold titles of each dev split)
  dataset      unique gold titles  present exactly  Recall ceiling  measured Recall@5
  2Wiki        23,561              65.0%            0.6727          0.3008  (45% of ceiling)
  HotpotQA     13,783              87.3%            0.8760          0.5078  (58% of ceiling)
  MuSiQue       2,328              81.7%            0.8724          0.2032  (23% of ceiling)
  Questions where ALL gold titles are present in the corpus:
  2Wiki 44.6%, HotpotQA 77.1%, MuSiQue 69.1%.
  ("Recall ceiling" = mean over questions of |gold titles present in corpus| /
   |gold titles|, i.e. the maximum value RecallAtK can take.)

WHAT TO DO
  1. Add cmd/coverage: given -dataset and -corpus, stream the corpus once,
     collect the set of titles via flashrag.PassageTitle, and report:
       - number of unique gold titles and how many are present,
       - the Recall ceiling (mean per-question fraction present),
       - the share of questions with every gold title present.
     Write a .tex fragment (\<Name>RecallCeiling, \<Name>GoldTitlesPresent,
     \<Name>QuestionsFullyCovered) into paper/.
     Streaming the 14 GB corpus takes a few minutes; do not load it into RAM
     other than as a title set.
  2. Report Recall@K both absolutely and as a fraction of the ceiling in the
     results tables.
  3. State plainly in the paper that MuSiQue at 23% of its ceiling is
     retrieval-bound, while 2Wiki is corpus-coverage-bound.

HOW TO VERIFY
  Reproduce the numbers above exactly (they were computed with the same
  definition and exact string matching).

--------------------------------------------------------------------------------
A4. Gold-title matching is exact-string, so case/unicode differences count as
    retrieval failures.
--------------------------------------------------------------------------------
WHERE
  pkg/flashrag/dataset.go (GoldTitles, PassageTitle), consumed by
  cmd/bench/main.go (evaluate) and cmd/diagnose/main.go (scanCorpus).

WHAT IS WRONG
  Titles are compared byte-for-byte. Differences in case, unicode composition
  and whitespace make an article that IS in the corpus count as missing. This
  understates Recall@K and MRR, and overstates "gold article not in corpus" in
  the diagnosis.

EVIDENCE
  Applying NFKC + lowercase + whitespace collapse to both sides recovers:
    2Wiki    +4.5 pp of gold titles  (Recall ceiling 0.6727 -> 0.7260)
    HotpotQA +2.2 pp                 (0.8760 -> 0.8987)
    MuSiQue  +2.0 pp                 (0.8724 -> 0.8867)

WHAT TO DO
  1. Add to pkg/flashrag:
       func NormalizeTitle(s string) string
     doing unicode NFKC normalisation, lowercasing, and collapsing runs of
     whitespace to a single space, then trimming. Document why each step is
     there.
  2. Use it on BOTH sides everywhere titles are compared:
       - cmd/bench/main.go evaluate: normalise `titles` and `gold` before
         RecallAtK / ReciprocalRank.
       - cmd/diagnose/main.go scanCorpus and the `wanted` set.
       - cmd/coverage (A3).
  3. Do NOT change PassageTitle's quote trimming - the corpus legitimately
     mixes quoted and unquoted titles and Trim already handles both.

HOW TO VERIFY
  Recall@5 on 2Wiki should rise by roughly 1-3 points; \DiagTwoWikiNotInCorpus
  should fall. Both need a re-run unless B1 is done first (then the retrieval
  metrics can be recomputed from the dumps).

B2. Recall is computed over the whole context but labelled Recall@TopK.
--------------------------------------------------------------------------------
WHERE
  cmd/bench/main.go:398  ->  metrics.RecallAtK(titles, gold, len(titles))
  cmd/bench/main.go writeTex -> emits \<Name>RecallAtK next to \<Name>TopK

WHAT IS WRONG
  The choice itself is correct and deliberate (documented in the comment above
  evaluate): trimming IRCoT's accumulated set to top-k would discard exactly
  the passages its extra rounds fetched. The REPORTING is what is wrong. The
  generated .tex writes \IRCoTTwoWikiRecallAtK{0.3577} alongside
  \IRCoTTwoWikiTopK{5}, next to \NaiveRAGTwoWikiRecallAtK{0.3008} with
  \NaiveRAGTwoWikiTopK{5}, which reads as a same-K comparison and is not one.

EVIDENCE (mean passages actually in context, from runs/)
  naive 5.00 everywhere; naive10/crag10 10.00 everywhere;
  crag 5.17 (2Wiki) / 5.33 (HotpotQA) / 5.33 (MuSiQue);
  ircot 8.77 (2Wiki) / 7.33 (HotpotQA) / 9.32 (MuSiQue).
  Passage-count distribution:
    crag-2wiki:  5:87.8%  6:8.3%  7:3.4%  8:0.4%  9:0.1%
    ircot-2wiki: 5:33.7%  ...  10:16.0%  15:11.0%

WHAT TO DO
  1. Rename the emitted command to \<Name>RecallAtContext (or keep the name
     but stop emitting \<Name>TopK for multi-round architectures).
  2. Always emit \<Name>MeanPassagesInContext and put it in the results table
     as its own column.
  3. Keep the naive10 / crag10 matched-budget controls - they are the correct
     answer to this and should stay in the paper.

B3. No log of the decisions CRAG and IRCoT actually made.
--------------------------------------------------------------------------------
WHERE

WHAT IS WRONG

  3. Report the branch distribution in the paper (a CRAG whose corrective

B7. No correction for multiple comparisons.
--------------------------------------------------------------------------------
WHERE
  cmd/compare/main.go (the seven report() calls), and the paper's claims.

WHAT IS WRONG

B8. -max-answer-tokens caps the intermediate LLM calls too.
--------------------------------------------------------------------------------
WHERE
  cmd/bench/main.go:146 and :152 (gen.MaxTokens = *maxAnswer), used by
  pkg/rag/ircot.go (reasoning step), pkg/rag/crag.go (grade, rewrite)

WHAT IS WRONG

    paper/ contains only *.gen.tex fragments and no main .tex that \input{}s

C5. No rerank results exist.
    pkg/rag/rerank.go is implemented and the vllm-rerank container is running,

    five commands already written in README, then add the matching
    cmd/compare runs (rerank vs naive, and rerank vs naive10 as the
    matched-budget control - rerank keeps top-k 5 while spending one
    cross-encoder pass, so both comparisons are informative).
    NOTE: pkg/provider/vllm.go Rerank sends full passages with no

================================================================================
SECTION D - MISSING BASELINES
================================================================================

D1. BM25 / hybrid retrieval.
    There is no lexical baseline at all. README itself claims keyword search is
    worth "12-25%", and many 2Wiki questions are literally exact title matches
    ("Which film has the director died earlier, Poker In Bed or The Machine To
    Kill Bad People?"). A reviewer will ask for this immediately. Qdrant
    supports sparse vectors; alternatively index titles separately.

D2. A routing / self-assessment baseline (Self-RAG or Adaptive-RAG).
    CRAG is present, but the diagnosis points at routing and abstention as the
    largest available gain, and there is currently no baseline in that family.

D3. Neighbour expansion - verify or retract the README hypothesis.
    README "Foundation" claims pulling the neighbouring passages of the same
    article is worth "28-42%". The project's own diagnosis says the
    answer-bearing article was already in the top-k but the wrong slice was
    taken in only 5.0% (2Wiki) / 6.7% (HotpotQA) / 5.3% (MuSiQue) of failures.
    The repo currently contradicts itself. Either measure the variant or fix
    the README.

  - Skip 2Wiki (12,576 questions) and TriviaQA (11,313) in B and C: together

STATISTICAL POWER - IMPORTANT
  The effects being measured are ~1.0-1.3 percentage points of EM. At
  n = 2417 (MuSiQue) a paired test cannot detect that; this is already visible
  in the existing results (IRCoT vs naive10 on MuSiQue: +0.0054, p = 0.3122).
  In configs B and C, report the DIRECTION and the confidence interval of the
  difference, not "significant / not significant", and frame it as replication
  rather than as new evidence.

FRAMING
  Do not present B and C as "checking whether the results are the same" -
  absolute EM will certainly change. Present them as "checking whether the
  ranking of architectures and the sign of the difference hold". That is what
  the "encoder-specific / model-specific" objection actually asks.

FACTS ESTABLISHED WHILE BUILDING THEM (do not re-derive)
  - The corpus is NOT laid out in article order. Passages of one article are
    near each other but interleaved with others: ids 29, 31, 32 are "Absalon"
    while 30 is "Pseudorandom generator". In a 200k-line sample, 38% of
    multi-passage articles have non-contiguous ids. Neighbour expansion by
    id +/- 1 would therefore be wrong, which is why TitleIndex exists.
  - dataset/wiki18_100w.titles.gob: 3,232,908 articles, 21,015,324 passages.
    Built in 1m32s, 159 MB on disk, gitignored by the existing dataset/* rule.
    It reproduces the corpus title count from A3 exactly, which is a useful
    cross-check that PassageTitle handles both the quoted and the unquoted
    title form.
  - The lexical ingest runs at ~15,000 docs/s with no GPU, so the full
    21,015,324-passage index takes roughly 25 minutes. This is why the hybrid
    is built as a SECOND collection fused client-side rather than as a
    re-ingest of the dense one: the dense vectors are never recomputed.
  - Mean passage length is 98.2 indexed tokens, which is the BM25 avgdl.
  - Qdrant v1.19 request shapes were verified live against a throwaway
    collection: sparse create ("vectors": {} + "sparse_vectors" with
    "modifier": "idf"), sparse upsert, /points/query with
    {"query": {"nearest": {...}}, "using": "text"}, and /points for
    retrieve-by-id. The Query API returns result.points, NOT result.

DESIGN DECISIONS WORTH KEEPING (and defending in the paper)
  - RRF fuses ranks, not scores, because a cosine similarity and a BM25 score
    are not on a comparable scale. k = 60, the value from Cormack et al.
  - Term ids are a 32-bit FNV-1a hash of the token, so no vocabulary has to be
    built, stored or shipped. Expected collisions: ~3000 term pairs out of ~5M
    distinct terms.
  - Qdrant's "idf" modifier supplies the inverse document frequency, so the
    client never makes a second pass over the corpus to count document
    frequencies. The client stores only the BM25 term-frequency saturation
    factor; the query vector carries 1.0 per term.
  - HyDE encodes the draft with the DOCUMENT prefix and the question with the
    QUERY prefix, because that is what each of them is. For bge-base-en-v1.5
    both are empty and it is a no-op, but it will matter for the E5 run in
    section F.
  - HyDE averages the question's embedding into the search vector (the
    paper's f(q)), so a draft that goes off topic degrades the search towards
    plain NaiveRAG instead of chasing a hallucination.
  - AdaptiveRAG is built out of the existing ClosedBook / NaiveRAG / IRCoT
    objects rather than reimplementing them, so its rows stay comparable with
    theirs and it adds exactly one classification call.
  - NeighbourRAG emits each hit BEFORE its own neighbours and keeps the hits in
    retrieval order, so every originally retrieved passage keeps its rank and a
    change in MRR reflects what was added rather than a reshuffle.
  - The lexical query is built from the raw question, never the prefixed one:
    an embedding-model instruction would only add noise terms to an inverted
    index.
